# v3.0.3 refresh path audit

This note separates the two actions that can be called “Manual Refresh” from
LiveContainer Home's Refresh All action.

## LiveContainer refresh settings and Home

The settings row (“Refresh SideStore now”) and Home’s “Refresh All” button use
the same scheduler entry point, the same runNow / execute(source: manual)
flow, the same network preflight, the same RefreshAllAppsIntent XPC bridge,
the same SideStore background refresh operation, and the same manifest and
guest verification. They differ in the generated request_id and origin
(refreshManager versus home) so each UI attempt owns only its own result.

## Native SideStore app-list refresh

MyAppsViewController.refreshAllApps obtains targets with
InstalledApp.fetchAppsForRefreshingAll and calls AppManager.refresh.
AppManager.refresh starts the normal PipelineRunner with the selected app
list and reports its result through the refresh group. This visible SideStore
screen does not run LiveContainer's Wi-Fi / LocalDevVPN preflight, produce a
host request ID, write the LiveContainer verification manifest, or verify
guest signatures.

The Home/settings scheduler path instead calls the existing
RefreshHandler.startRefresh XPC bridge. SideStore runs RefreshAllAppsIntent,
which calls AppManager.backgroundRefresh and then
BackgroundRefreshAppsOperation. That path checks saved authentication
material, observes running apps, applies the existing SideStore refresh
pipeline, writes a version 2 manifest, and returns the result over XPC. The
host checks the same run ID in the manifest, verifies each attempted result,
checks installed guest signatures, and checks installed host-profile renewal
when SideStore replaces LiveContainer.

## Corrected target and result contract

The background SideStore operation previously omitted currently running apps
from its attempted list while the manifest still expected the original full
list. The host correctly rejected that manifest as incomplete, even when the
attempted apps had valid results.

A correlated user-initiated host run now uses the full list returned by
fetchAppsForRefreshingAll, matching the native manager's target list.
Scheduled background runs retain SideStore's running-app exclusion. Both paths
write requested_ids, expected_ids (the apps actually attempted), and
skipped_ids. The host accepts only a complete result set for the manifest's
exact run ID and reports any skipped running apps in the terminal message.

The two LiveContainer scheduler buttons now have the same target policy as
well as the same engine. Their distinct request and run IDs prevent a prior
settings completion or failure from satisfying Home.

The host stores each terminal result in a ledger keyed by run_id, with the
originating request_id in the same record. It commits the verified manifest,
clears active-run ownership, commits the terminal record, updates health, then
publishes the state change and completion notification. A Home request reads
only the ledger entry matching both its request ID and its assigned run ID.

This path analysis identifies the concrete target-list / manifest mismatch in
the previous implementation. The device's health=REFRESH_FAILED report did
not include the terminal stage or manifest, so that one run's exact failing
branch cannot be established from the supplied diagnostic. The candidate now
preserves the exact current-run failure record and target counts for device
retesting.
