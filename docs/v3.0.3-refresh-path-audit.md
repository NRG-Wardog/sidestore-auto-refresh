# v3.0.3 refresh and install path audit

## Setup Test Refresh and Home Refresh All

Setup Assistant Test Refresh, Home Refresh All, and the LiveContainer refresh
settings action all post `LiveContainerAutoRefreshRunNow`. The host observer
passes each request to `LiveContainerAutoRefreshScheduler.runNow`, which calls
the same `execute(source: "manual")` flow. That flow performs the same network
preflight, `RefreshHandler` XPC call, SideStore background refresh operation,
run-bound verification manifest check, guest-signature check, and terminal
ledger write. Origin and request ID differ (`setupAssistant`, `home`, or
`refreshManager`); they do not select a different signing or target algorithm.

Each request still gets a new request ID and run ID. A previous Setup success
cannot satisfy Home. The reported Home failure was typed as a signing-stage
`signingNetworkConnectionLost` during `provisioningProfileFetch`, while its
network preflight had passed. That identifies an interruption during that
provisioning request. It does not prove LocalDevVPN or the current connection
is persistently misconfigured. The safe recovery text now asks for one retry
and recommends Connection Check only if the failure repeats.

The current run record and Copy Diagnostics include request/run IDs, origin,
network-preflight result, failure stage/cause/source step, and bounded requested,
attempted, and skipped app identifiers when the service returned a manifest.
They keep the result tied to the current run even when the raw error domain is
redacted.

The visible native SideStore app-list refresh is a separate path:
`MyAppsViewController.refreshAllApps` calls `AppManager.refresh` directly. It
does not run LiveContainer's preflight, request/run correlation, verification
manifest contract, or guest-signature check. A success there does not prove a
different LiveContainer scheduler attempt succeeded.

## Local IPA and URL install

The local-file path is:

`UIDocumentPicker -> private App Group staging -> UUID token -> operation UI -> service resolves staged IPA -> AnyApp`

The URL path is:

`URL handler -> URL download -> temporary local IPA -> AnyApp`

The first convergence point is `makeDriver` after either resolver returns an
`AppProtocol` in `InstallTarget.app`. Both routes then use the same
`makeInstallDriver`, construct `AppOperation.install`, and call the same
`PipelineRunner.performSingleOperation` with the same signing/install prompts
and terminal-result handling. Route diagnostics retain only the route name and
opaque operation session; they do not log local file paths.

The silent first picker attempt occurs before this convergence point. A snapshot
reload could still own `status.loading` when the picker sheet's dismissal
callback tried to assign the full-screen operation presentation. The old
handoff rejected that request; a later picker attempt happened after the reload
and was accepted. The new handoff keeps the staged token in the status store,
waits for the actual picker-dismiss callback and for `loading` to clear, then
assigns the operation presentation once. It uses state transitions rather than
a delay.

## Delete terminal state

The delete driver now records successful return from SideStore's native
uninstall operation, independently observes the saved `InstalledApp` library
state in Core Data, and still accepts the normal `PipelineRunner` callback.
Progress does not decide success. The operation completes when the pipeline
callback succeeds and the authoritative app-library record is absent. If the
full callback is delayed or missing, native-uninstall success plus authoritative
absence can complete after a bounded reconciliation window. Library absence by
itself cannot fabricate success.
